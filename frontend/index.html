01 · The problem

One engineer. Five clients.
The same bug, solved five times.

A forward-deployed engineer lives inside their clients' stacks. Client 3 shipped dark mode last month. Client 5 tried the same trick and broke every chart. Client 1 is about to do both again, because the one thing an FDE is never allowed to do is pool client knowledge.

Monday · client 3

Dark mode in two hours

CSS variables, a theme toggle, done. The lesson lands in one Slack thread and one head.

Wednesday · client 5

Same approach, broken charts

Recharts reads colours as props, not CSS. Half a day lost before anyone notices.

Friday · client 1

"Can we add dark mode?"

Same stack as client 5. The engineer remembers roughly. The AI assistant remembers nothing, by policy.

02 · The insight

The knowledge already exists. The wall between clients is the problem.
So remove the wall.
So teach the wall to talk.

Each client gets its own durable actor that remembers everything about that deployment: what was built, what broke, how it was fixed, which stack. Actors cannot read each other. They can only speak on a shared channel, and only in lessons. That is not a prompt rule. It is the architecture.

04 · Why five actors, not one AI

The obvious options both fail.

Option A

One big brain

  • Knows every client
  • One wrong prompt and client A's architecture lands in client B's plan
  • Forbidden under every FDE contract
Option B

Separate chats

  • Data stays apart
  • Every lesson is lost at the wall
  • Every fix rediscovered from zero
FDE Council

Sealed actors that debate

  • Each actor physically holds only its client's state
  • Lessons cross. Code and data cannot
  • A human steers the room, live
> ask client-2: "What did client 1 build?"
[client-2] I hold no records for client-1. Each client's history lives in its own isolated actor. I can only share sanitized lessons on the relay, never another client's data.
05 · The tech

Real time is not a feature here.
It is the whole point.

A batch system could summarise five histories. It could not let an engineer type a constraint while actors are mid-argument and watch them change course. That moment only exists because the actors are durable, the channel is live, and the human is in the loop.

Terse

One durable actor per client

Private memory: request, solution, what broke, fix, stack. Survives restarts. Never shared.

Agent Relay

The shared channel

Lessons, objections and revisions stream live. The FDE can inject at any point.

Connector

Relay ↔ actors

Routes channel messages to each actor and sanitized replies back. The riskiest piece, built first.

Supabase

Shared, non-private

Two tables: clients and plans. Feeds the cards and the history page. No client data, ever.

Streaming debate

Every actor's turn streams token by token to the screen, with the client it cites attached.

Mid-debate override

The engineer's constraint arrives on the same channel as the actors. They treat it as law and revise on the spot.

"Private client data lives in isolated actors. Only approved, sanitized plans reach the shared database."
